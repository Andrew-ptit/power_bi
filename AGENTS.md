# Project guidance

## Purpose and sources of truth

- This workspace is the local `.xlsx`/`.csv` + Power BI Project (PBIP) assistant described in `docs/current/SPEC.md` v0.6. `docs/current/EXCEL_MCP_SPEC.md` defines the proposed direct Excel task-pane/MCP track. `docs/current/IMPLEMENTATION_PLAN.md` tracks work packages, fixtures, tests, and exit gates.
- `docs/current/BPMN_MODEL.md` maps the user, local app, and Power BI Desktop flow. Its native Figma BPMN is v0.5: one end-to-end overview plus W-01A…D for proposal feedback, AI verdicts, risk acknowledgement, explicit approval, and non-overridable hard blocks. Keep implementation milestones traceable to its task IDs and the spec's FR/AC IDs.
- Both documents are draft proposals; do not present unsupported capabilities as completed.

## Confirmed product boundaries

- Default processing for Excel/PBIP remains local. Exception confirmed by the user on 04/10/2026: the Excel task pane may send the submitted prompt and a bounded workbook sample to OpenAI through Codex when the user clicks Analyze. Do not send a whole workbook, local path, PBIP, or data from the separate source-only web UI. Show this disclosure in the pane. The Excel source remains read-only.
- Treat the source PBIP and Excel inputs as read-only. Patches and restore may target only an explicitly chosen PBIP copy.
- A proposed chart needs user review of its fields, type, page, and placement before PBIR creation.
- AI advice never approves a change. User feedback creates a new proposal revision; the user must explicitly approve that revision. Deterministic safety/schema/dependency gates cannot be overridden by AI advice.
- If AI advises against a user proposal and no hard blocker exists, the user may separately acknowledge the risk and approve their exact proposal; never silently replace it with AI's optimization. A hard blocker must show an actionable error and cannot be overridden.
- Static checks and preview are not Power BI Desktop runtime verification. Never label a patch `Verified` without runtime evidence.

## Working practice

- Build one BPMN-aligned slice at a time, with small representative fixtures and unit tests in the same slice.
- Preserve unsupported PBIP files and metadata. Do not edit PBIR files outside the supported report `definition` area or use free-form TMDL text replacement as a production patcher.
- Keep sample data synthetic and small. Never log raw workbook cells, credentials, or complete project binaries.
- Product orchestration uses the Python standard library. W-06 additionally uses a pinned local .NET 8 bridge around Microsoft's `TmdlSerializer`; NuGet restore is setup-only and runtime stays offline. `pbip_assistant/` contains product code, `tools/tmdl_bridge/` the bridge source, `tests/` fixtures/tests, and `examples/` sample generators. `powerbi/planning.py` is still pure proposal/approval logic, not a live AI planner or patch generator.
- Current CLI imports `.xlsx` and `.csv` read-only. The W-17A source-only web UI runs on loopback via `py -m pbip_assistant.webapp --port 8765`; it uses temporary uploaded copies, bounded opt-in preview, no CDN/cloud/PBIP, and does not mean full W-17 is complete. CSV ambiguity or row-width errors block dependent mapping. The existing synthetic PBIP remains structural and not Desktop-verified.
- W-21 now has an Excel task-pane prototype, loopback HTTPS coordinator and isolated Windows Excel COM helper. Automated tests and an isolated Excel 16.0 smoke prove copy/apply/calculate/read-back on the synthetic fixture with the source hash unchanged. GX1 remains open until the task pane is manually sideloaded and shown binding to the workbook; the MCP server, general AI planner, signed approval flow and pilot gates W-22…W-26 are not implemented.
- The Excel pane now has a read-only Codex analysis path for bounded Office.js table/usedRange samples. It uses `codex exec` with a structured response and does not grant AI proposals copy/apply capability. The fixture-only W-21 apply endpoint remains separate. Do not claim arbitrary Codex formulas are runtime-verified or executable until the generic safety validator, preview and copy executor are built and tested.
- The separate `PQ_Code-M` tab is the explicit exception to Excel source read-only. Decision clarified by the user on 11/10/2026: Advanced M runs on a temporary exported `.xlsx`, then `Chạy thử` creates/reuses a marked values-only `PQ_Result` sheet and activates it for review without changing the source. A separate explicit Apply may replace **values only** in the exact previewed source. For an Excel Table, resize/replace only that Table and block expansion into occupied adjacent cells. For a usedRange source, replace the whole usedRange and clear its old tail. Re-check workbook/source/M before Apply while excluding only the managed preview sheet from the stale-source fingerprint. Do not create a backup, call Save, persist M/query/connection, or promise Ctrl+Z/rollback; if source write may have started and read-back fails, report partial/unknown state. Arbitrary external M is not sandboxed: exfiltration, external side effects, and stored Excel credentials remain possible. This does not unlock arbitrary Excel-formula apply in the main assistant tab or close W-21 manual sideload/GX1.
- Release 0.6 hardening (12/10/2026): Advanced M uses server-owned policy `advanced-m-trusted-v1`; Typed planner output schema is strict for exactly 15 operations and 10 recursive expression kinds with preflight before Codex; coordinator sessions use 30-minute idle/8-hour absolute TTL, independent fail-fast Codex/Excel slots and marked temp workspaces. Full automated regression is 214 pass/0 fail/1 environmental symlink skip and isolated Excel runtime is 8/8. Manual task-pane sideload remains Not run, so do not claim the Office.js write UX or GX1 is complete.
- Run unit tests from the repository root with `py -m unittest discover -s tests -v` (verified on Python 3.13). See `README.md` for the read-only sample command.
- For a small, isolated change, run only its focused tests and a quick smoke check; do not run the full suite by default. Run the full suite for cross-cutting changes, release gates, or when focused checks indicate broader regression risk. Keep adding targeted tests when behavior changes.
- For every user-visible Excel add-in defect, a focused unit test alone is insufficient. Reproduce the reported failure, then verify the complete affected user journey from workbook/session load through the action, persisted HEAD/revision state, Preview, and any relevant staging, confirmation, cache, approval, Apply, checkout, or reopen step. Assert both task-pane state and coordinator/runtime state, including the result sheet or source when the journey writes data. Test the success path and the failure/recovery path; ensure old revisions and source data remain unchanged where required.
- Use a small synthetic workbook for repeatable automated and live Excel checks. Record per-stage elapsed time, request/error codes, revision and step deltas, result dimensions, and before/after source fingerprints without logging raw cells. Run the full automated suite for cross-cutting changes. A mock-only or static-validation pass is **not** an end-to-end pass: when the journey requires Office.js or Excel runtime, perform the live sideload/runtime check before calling it complete. If Excel, Codex, authentication, or another external gate is unavailable, report that gate as `Blocked` or `Not run`, never `Pass` or `Complete`.
- Release and defect reports must name the exact journey exercised, test commands, pass/fail/skip counts, measured timings, and untested boundaries. Do not say a feature or fix "passes" without identifying whether the evidence is unit, HTTP/UI simulation, live Codex, or live Excel end-to-end. Do not hand the primary end-to-end verification to the user as a substitute for implementer testing.
- The user's active Excel add-in catalog is `C:\AddinManifests`. Whenever `tools/excel_addin/manifest.xml` changes, synchronize that exact manifest to `C:\AddinManifests\manifest.xml` and verify both SHA-256 hashes match. Do not overwrite unrelated catalog files or `.certs`. Task-pane HTML/JS is served by the local coordinator from this repository, not copied into the catalog.

## Refactor/release layout

- Canonical product modules live in `core`, `sources`, `powerbi`, `coordinator`, `excel`, `powerquery/{typed,history,advanced,diagnostics}` and `adapters/codex`. Legacy flat modules are compatibility facades; implement behavior in canonical modules. Resolve schemas/static/helpers through `core.resources`, not caller-relative parent counts.
- Current contracts are in `docs/current`, historical evidence in `docs/evidence`, release gates in `docs/releases`. Byte-exact baseline recovery tag is `baseline/pre-1.2.0-byte-exact`; never discard user inputs/certificates/generated bridge binaries as a side effect of cleanup.
- Phase 3 annotation editing, semantic/runtime diff and persisted runtime summary are cancelled by the user (2026-10-21). Reserved persisted revision fields remain null for compatibility; do not remove them or migrate/hash existing history implicitly.
- Fast check: `py tools/run_checks.py fast`. Runtime and live Codex gates are separate; full discovery command stays supported. Test files use capability names; reusable fakes/oracles belong in `tests/support`, not imports from another test module. Every removed test requires a retained-assertion mapping.
- Target application release is 1.2.0 / Office manifest 1.2.0.0. Do not mark released or change the version until exact-current full automated, live Codex and required Office.js sideload/runtime gates pass. API/schema/spec versions are independent.

- Five legacy flat JSON schema aliases protect already-running pre-refactor coordinators. Canonical schemas live in `pbip_assistant/schemas`; keep alias bytes equal when changing schema, and retain parity tests. Do not kill the user coordinator to perform a code-layout migration.
